# Engineering Review and Pipeline Hardening — Done

Status: DONE
Date: 2026-08-25

## Objective

Review the Social Content Production Cockpit code path as a senior process/software engineering pass, identify production risks, implement low-risk hardening, and document the updated process.

## Scope Reviewed

Primary files reviewed:

- `marketing-content-os/apps/social_pipeline_desktop/main_workspace_parallel.py`
- `marketing-content-os/apps/social_pipeline_desktop/workspace_parallel_service.py`
- `marketing-content-os/apps/social_pipeline_desktop/pipeline_service.py`
- `marketing-content-os/tools/clean_validate_campaign_markdown.py`

The review focused on:

1. GPT1 raw-file preservation;
2. generated output rebuild behavior;
3. rerun modes and workspace-level summary integrity;
4. GPT2-ready package generation;
5. diagnostics and operator observability;
6. prevention of generated files being mistaken for GPT1 raw inputs.

## Findings

### Finding 1 — Generated files could be discovered as raw input in direct service use

`workspace_parallel_service.py` normally calls `clean_folder()` on each SKU `raw/` folder, which is safe. However, `pipeline_service.discover_raw_files()` is also usable directly by other scripts/tools. Its ignored folder list did not include newer generated folders such as:

```text
_diagnostics/
_runs/
.git/
.venv/
__pycache__/
```

Risk: if a direct operator/tool call points at a broader workspace, generated diagnostic/readme text files could be treated as GPT1 raw inputs.

### Finding 2 — Per-file batch summary lacked enough diagnostic fields

`pipeline_batch_summary.json` did not expose the cleaner report result, normalizer version, auto-fix count, validator exit code, or validator message. Workspace-level summary had improved diagnosis, but per-file summary still needed better audit visibility.

### Finding 3 — Rerun rebuild policy must remain explicit

Recent patches now clear per-SKU generated outputs before processing. This policy should remain a hard rule:

```text
rerun selected SKU
→ preserve raw/
→ delete _cleaned/
→ delete _ready_for_gpt2/
→ rebuild from raw/
```

## Implemented Changes

### 1. Hardened raw discovery

`pipeline_service.py` now centralizes ignored generated/system folders in `IGNORED_RAW_PARTS` and uses `_is_ignored_raw_path()` during raw discovery.

This reduces the chance that generated files from `_diagnostics`, `_runs`, `.venv`, `.git`, or cache folders are ingested as GPT1 outputs.

### 2. Expanded `CleanResult` diagnostics

`CleanResult` now carries:

```text
report_result
normalizer_version
auto_fix_count
```

These values are read directly from the cleaner report generated by `clean_validate_campaign_markdown.py`.

### 3. Expanded `PipelineBatchSummary`

`PipelineBatchSummary` now includes `auto_fix_count` at batch level and writes the following fields per result:

```text
report_result
normalizer_version
auto_fix_count
exit_code
message
```

This improves diagnosis without requiring the operator to manually open every low-level cleaner report.

## Process Design After Hardening

The intended production flow is:

```text
GPT1 raw files in raw/
  ↓
discover only allowed raw suffixes outside generated/system folders
  ↓
clear generated outputs for the selected SKU before rerun
  ↓
clean/normalize/validate
  ↓
write clean TSV + report
  ↓
write selected rows + enriched GPT2 prompts
  ↓
copy into _ready_for_gpt2
  ↓
write workspace summary with diagnosis
```

## Acceptance Expectations

A healthy full run over the current 24-SKU workspace should remain:

```text
24 SKU jobs
24 pass
0 fail
24 raw GPT1 files
240 ready GPT2 prompts
```

A recoverable whitespace issue should continue to be reported as:

```text
PASS_WITH_AUTOFIX
```

and not block production.
